# design — contract harness

Локальний TypeScript CLI: читає авторські `design.mdx`, виділяє контракти з блоків `ts design`, перевіряє їхню узгодженість із реалізаціями та тестовими деклараціями і готує матеріали для LLM-рев’ю. Специфікація MVP: [docs/contract-workflow-mvp.md](docs/contract-workflow-mvp.md). Відхилення від неї та пропозиції змін: [docs/plan-proposals.md](docs/plan-proposals.md).

**Статус:** готові етапи «Технічний зріз» і «Витягування». Працює команда `design extract`. Директиви (`@contract`, `@invariant`, …), реалізації й тести харнес ще не читає.

## Розробка

Потрібен Node.js ≥ 24.11. Перевірено на 24.21.0 і 26.10.0.

```sh
npm install
npm run typecheck   # tsc для src і test
npm test            # node:test, запускає .ts напряму без збірки
npm run build       # dist/
npm run verify      # усе разом і запуск зібраного CLI
```

## Використання

```sh
design extract           # перевіряє дизайни й записує design.generated.ts поруч із кожним design.mdx
design extract --check   # те саме без запису: для CI
```

| Прапорець | Значення |
| --- | --- |
| `--root <path>` | Корінь проєкту; типово поточний каталог |
| `--config <path>` | Конфігурація, шлях від кореня проєкту; типово `.design/config.json`, якщо є |
| `--format text\|json` | Формат звіту; типово `text` |
| `--help`, `--version` | Довідка та версія |

Звіт іде в stdout, помилки аргументів — у stderr. Коди виходу: `0` — успіх; `1` — помилки в дизайнах або неактуальні generated-файли; `2` — некоректні аргументи, конфігурація чи середовище (tsconfig, файлова система).

### Що робить `extract`

1. Знаходить усі `.design/design.mdx` за конфігурацією.
2. Перевіряє design-фазу всього scope: синтаксис MDX, блоки `ts design`, типи.
3. Порівнює кожен `design.generated.ts` на диску з текстом, зібраним зі свіжого MDX, і записує лише відсутні та змінені файли.

Нічого не записується, якщо в будь-якому дизайні є помилка або хоч один output у конфлікті. Конфлікт — це файл на місці output без заголовка власності (`// @generated by design; DO NOT EDIT.`), symlink або каталог. Файл із заголовком вважається керованим: ручні правки в ньому `extract` замінює текстом із MDX.

Статуси outputs у звіті: `written`, `unchanged`, `missing`, `stale`, `conflict`, `failed`. З `--check` відсутній, застарілий або чужий файл дає `E_GENERATED_MISSING`, `E_GENERATED_STALE`, `E_GENERATED_CONFLICT`. Після видалення `design.mdx` його generated-файл лишається на диску; видаляти його треба вручну.

### Конфігурація

`.design/config.json` необов’язковий. Типові значення:

```json
{
  "version": 1,
  "tsconfig": "tsconfig.json",
  "designs": ["src/**/.design/design.mdx"],
  "implementations": ["src/**/*.ts"],
  "tests": ["src/**/*.test.ts", "tests/**/*.test.ts"],
  "exclude": ["**/node_modules/**", "**/dist/**", "**/build/**", "**/coverage/**"],
  "testAdapter": "node:test"
}
```

- `version` обов’язковий; невідомі поля та неправильні типи — помилка `E_CONFIG`.
- Пропущені поля беруть типові значення; заданий масив замінює типовий повністю.
- Шляхи й шаблони рахуються від кореня проєкту.
- `**` і `*` не збігаються з dot-каталогами: `.design` у шаблоні треба назвати явно.
- Дизайном є лише файл `.design/design.mdx`; інші файли, що збіглися з шаблоном, ігноруються.
- Symlink під час пошуку не обходяться.
- `implementations`, `tests` і `testAdapter` уже перевіряються, але ще не використовуються.

## Як влаштована design-фаза

Перевірки йдуть шарами; наступний шар запускається, лише коли попередні не знайшли помилок у всьому scope, бо інакше його результати були б наслідками тих помилок.

1. **Документи.** MDX лише розбирається (`unified` + `remark-parse` + `remark-mdx`), не виконується. Беруться блоки `ts design` верхнього рівня без відступу. Коди: `E_MDX_SYNTAX`, `E_DESIGN_BLOCK_MISSING` / `_EMPTY` / `_MARKER` / `_LOCATION`.
2. **Блоки.** Кожен блок має бути завершеним TypeScript сам по собі: незакрита `{` чи `/*` не може поглинути наступний блок. `// @ts-nocheck` заборонений.
3. **Типи.** Блоки одного документа склеюються в модуль за §4.4. Модулі всіх дизайнів подаються компілятору з пам’яті за шляхами їхніх `design.generated.ts`; файли на диску не потрібні й не читаються замість них.

Усі діагностики компілятора ведуть на рядок і колонку оригінального MDX.

## Технічні рішення

- **TypeScript 6.0.3.** Npm `latest` для `typescript` тепер 7.x. Це нативний порт без стабільного Compiler API: пакет експортує лише `unstable/*`. Остання версія з документованим API — 6.x.
- **Опції проєкту.** Береться tsconfig проєкту з `extends`. Змінюються три речі: `noEmit: true`; `rootDir` ігнорується, бо стосується лише emit; опції, які TS 6 оголосив застарілими, але виконує (`baseUrl`, `moduleResolution: node10`), приймаються без помилки. Так харнес працює на проєктах із TypeScript 5.
- **Помилки конфігурації TypeScript** (синтаксис tsconfig, невалідні опції, відсутні `types`) мають код `E_ENVIRONMENT` і вихід 2. За них перевірка типів не запускається.
- **Мапінг.** Кожен скопійований рядок блока — окремий сегмент `generated offset → MDX offset`. Кінець тексту мапиться на кінець останнього авторського рядка. Те, що блок є дослівним фрагментом документа, перевіряється в коді.
- **BOM** на початку `design.mdx` відкидається при читанні; колонки рахуються без нього, як у редакторах.
- **Позиція помилки MDX** береться з `place`; для тегу, не закритого до кінця документа, парсер дає позицію лише в тексті повідомлення, звідти вона й читається.
- **Шляхи до бібліотеки TypeScript** у звітах мають вигляд `typescript/lib/lib.*.d.ts`, щоб звіт не залежав від місця встановлення харнесу.
- **Пошук файлів** — власний обхід каталогів із `path.matchesGlob`. Обхід заходить лише туди, де шаблон може збігтися.
- **Запис** — у тимчасовий файл поруч і `rename`. Порівняння з диском ігнорує різницю CRLF/LF і BOM. Збій запису одного файла не зупиняє запис інших; такий output має статус `failed`.
- **Порожній scope** (`E_NO_DESIGNS`) — вихід 1.
- **Тести** копіюють fixture в `test/.tmp/` усередині репозиторію, щоб копія знаходила `@types/node`, як справжній проєкт. Fixture `test/fixtures/vertical` містить три MDX, `package.json` і `tsconfig.json` із §13 дослівно; реалізації й тести з §13 з’являться на етапі «Зв’язування».

## Чого ще немає

Ці правила плану належать до наступних етапів; зараз харнес їх не перевіряє.

- Дизайн, що імпортує `design.generated.ts` модуля поза scope, читає цей файл із диска. Потрібен `E_DESIGN_OUT_OF_SCOPE` (§9).
- Value-імпорти, класи, функції та імпорти не з дизайнів у блоках `ts design` не відхиляються (§6.1, §9).
- JSDoc наприкінці блока в склеєному модулі стає коментарем першої декларації наступного блока. Парсер метаданих має читати JSDoc у межах одного блока (§4.4, крок 7).
- `@ts-ignore` і `@ts-expect-error` у блоках не діагностуються.
- На Windows харнес не запускався.
