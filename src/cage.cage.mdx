# cage

## Purpose

cage keeps a TypeScript project's specs, code and tests in sync, so that a coding agent is told what drifted before it hands the work back. The specs are `*.cage.mdx` documents next to the code; a contract in them is an interface the code must implement, an invariant a rule a linked test must check, and the review a recorded verdict that the tests really check the rules. cage runs locally, makes no model calls and runs no tests: the agent judges, the test runner runs.

This document is cage's own spec, checked by the published cage against this repository. The contracts are the harness's ports: the command line, the configuration and the legend of codes. Everything behind them — parsing documents, indexing designs, comparing types, reading tests, fingerprinting material — is implementation, listed in `.cageignore`.

## Glossary

- **Design**: the `*.cage.mdx` documents of one directory, read as one module.
- **Contract**: an exported interface marked `@contract`, implemented by code marked `@implements`.
- **Invariant**: a rule of a contract, `@invariant id text`, linked to tests marked `@covers id`.
- **Material**: what a review of a contract is about: its declaration, the prose of its module, its implementations, its linked tests with their setup, and the local dependency declarations or whole files included in its fingerprint.
- **Fingerprint**: a digest of the material, part by part; a recorded verdict is tied to it.
- **Dependency slice**: whole declarations selected from an imported local file, including the declarations they refer to transitively; it never selects individual methods of a class.
- **Fallback**: keeping a dependency file whole when its declarations or initialization effects cannot be separated reliably, with the existing bounds on following its imports.
- **Review**: a recorded verdict, per invariant, that the tests check the rule; an acceptance is a record without a verdict.
- **Diagnostic**: one finding of a check, with a code (`E_…` fails the check, `W_…` does not), the thing it is about and the place.

## Business rules

- A check is deterministic and never calls a model or runs a test. Green means the structure is in order and the recorded verdicts are for the material as it is now; it never means the tests pass or the verdicts are right.
- What was not checked is said as such, never counted as zero or passed.
- A diagnostic names the thing and the place; what it means and what to do about it is one place, `cage codes`.
- The agent reads reports by the hundred: a report shows what matters most and counts the rest, a packet carries facts and the lines that changed, never a lecture.
- A verdict is recorded only against the material as it is now, complete and with a reason and evidence; otherwise nothing is recorded.
- A review goes stale when its fingerprinted material changes, and the check names what. Ordinary code comments and spacing are context, not new review material under `code-v1`.
- A lock on a declaration is lifted only by a person, visibly, in the lock file; a lock the base branch has is never lifted on a branch.
- Nothing cage writes for a project overwrites what a person wrote.

### Dependency material

Dependencies are sliced only after a bounded check of their initialization and imported bindings. Unsupported cases keep the existing whole-file material. The implementation and tests of these rules are reviewed through the invariants below.

1. Dependency selection starts from the implementation statements and the linked tests, their effective setup and local helpers already selected as review material. Dependencies referenced by module-level initialization are also retained; recognized test/suite/hook registrations use the existing selection of linked tests and effective hooks. Implementations remain whole declarations, including whole classes. Shared methods and setup can therefore still make several contracts stale together.
2. Static named and default imports, aliases and explicit re-exports select their referenced declarations by binding, not by spelling alone. Each selected declaration includes its documentation and all same-file declarations it references, transitively. Imported classes are included whole. Multiple paths to a file contribute the union of their selections; falling back on any path makes that file whole.
3. A dependency can be sliced only when its module initialization is conservatively known to be inert. The initial supported subset is type declarations, function declarations, and `const` declarations initialized with primitive literals, function expressions or arrows, or arrays and ordinary objects composed of supported expressions. Parentheses, type assertions and unary signs on numeric literals do not change this classification. A reference to another constant is allowed only when its initializer is also in the subset. Function bodies are not executed during this classification; a selected function still brings its referenced declarations into the material.
4. Verify this initialization condition through the module's static value imports as well, including imports whose values the selected declarations do not use. An unused import can still execute code. Cycles, unresolved or opaque value imports, namespace imports, `export *`, CommonJS, side-effect-only imports, classes, decorators, top-level calls or `new`, mutable declarations, assignments, getters, spreads, computed properties and other unsupported syntax prevent slicing the affected module. A class dependency is therefore whole in this first version. Unknown effects must never be treated as proof that an import can be dropped.
5. Analyze only within the existing project boundary, exclusions, depth and file limit. A needed initialization proof that runs into a boundary is unavailable and requires fallback; it never authorizes reading beyond the boundary. Fallback uses the existing whole-file import traversal. Type-only imports remain excluded, and support for following dynamic imports or `require()` calls is not added in this change.
6. Keep one `dependency <file>` part, made from selected declarations and their connecting import/export statements in source order or the whole file on fallback, and count unique dependency files against `maxFiles`. Include the connecting import statements of an implementation or test in that implementation or test's material too: retargeting an alias must not preserve a verdict just because both targets were already selected elsewhere. Value imports with unknown or observable initialization remain connecting material even when their binding is unused, since retargeting or reordering them can change initialization order. Changes to selected declarations, their helpers, their bindings or their inclusion in the material must invalidate the review. Moving to fallback after a new side effect must also invalidate it. Line-number shifts alone must not change a slice's digest.
7. `check`, the review index, packet and recording use the same material. Changed dependency excerpts show the ranges actually fingerprinted; `--files all` still supplies whole files as context. No new warning or configuration switch is introduced. The gate's filtering of diagnostics is unchanged.
8. Keep the review-record format and existing part keys. Old records remain readable; when the new material differs, a fresh review is required. Do not silently translate a previous verdict or acceptance into approval of a different fingerprint.

For example, importing a literal constant from an otherwise inert module does not make an unrelated function body part of the review. A module with top-level `new Logger(...)` remains whole. This first version does not promise to eliminate every broad dependency warning in an application.

### Code fingerprints

New fingerprints use `sha256:code-v1:<digest>`. Implementations, tests, helpers and dependencies are hashed by their parsed syntax structure and literal token text, excluding ordinary prose comments and spacing. Selected declarations and whole-file fallbacks use the same rule. Source text and authored line ranges remain in packets; no separate explanation fingerprint is recorded. Parse errors conservatively keep the raw text.

Annotations containing `@`, triple-slash directives and recognized tooling comments (coverage, lint, formatting, bundler and source-map directives) remain fingerprinted, including their attachment to code. Line-sensitive suppressions also retain token line layout. File-wide compiler directives remain material even outside a selected declaration. Changes to runtime strings, templates, regular expressions, JSX text or syntax changed by automatic semicolon insertion are never discarded as formatting. This is syntax normalization, not a proof of behavioral equivalence.

The contract declaration and all design prose retain their exact text fingerprints: natural-language requirements are promises, not ordinary implementation comments. Unversioned `sha256:<digest>` records continue to use the existing source-text algorithm. Reading, checking and accepting already-current records never silently migrates them. A newly recorded verdict uses `code-v1`; legacy comment edits can still make a legacy record stale until it is reviewed under the new algorithm.

## Data

```ts design
/**
 * @data
 * @description What the command line gets from its environment: the working directory, what was piped in, where to write, and whether a person can answer a question.
 */
export interface CliIo {
  cwd: string;
  stdin?: string;
  stdout: (text: string) => void;
  stderr: (text: string) => void;
  ask?: (question: string) => string | null;
}

/**
 * @data
 * @description A place a diagnostic refers to besides its own: a message and, when known, a file, line and column.
 */
export interface RelatedLocation {
  message: string;
  file?: string;
  line?: number;
  column?: number;
  endLine?: number;
  endColumn?: number;
}

/**
 * @data
 * @description One finding of a check: a code, its severity, what it is about and where. Locations are project-relative POSIX paths, line and column from 1.
 */
export interface Diagnostic {
  code: string;
  severity: "error" | "warning";
  message: string;
  file?: string;
  line?: number;
  column?: number;
  endLine?: number;
  endColumn?: number;
  tsCode?: number;
  contract?: string;
  invariant?: string;
  related?: RelatedLocation[];
}

/**
 * @data
 * @description The bounds of the dependency part of a review's fingerprint: import levels followed, files fingerprinted per contract, patterns left out.
 */
export interface ReviewDependencies {
  depth: number;
  maxFiles: number;
  exclude: string[];
}

/**
 * @data
 * @description The project's configuration, every field present: the file's values over the defaults.
 */
export interface Config {
  version: 1;
  tsconfig: string;
  designs: string[];
  implementations: string[];
  tests: string[];
  exclude: string[];
  testAdapter: "node:test" | "vitest";
  review: "off" | "warn" | "require";
  coverage: "off" | "warn" | "require";
  reviewDependencies: ReviewDependencies;
  maxDiagnostics: number | "all";
}

/**
 * @data
 * @description A loaded configuration with what was wrong with the file, if anything; with a problem the defaults are returned.
 */
export interface LoadedConfig {
  config: Config;
  diagnostics: Diagnostic[];
}
```

## Contracts

```ts design
/**
 * @contract
 * @description The command line of the harness: runs one command for the given arguments and environment and returns the exit code. Reports go to stdout, usage errors and the gate's feedback to stderr.
 * @invariant exit-codes The exit code is 2 for a usage, configuration or environment problem, 1 when a rule is violated, 0 otherwise; warnings never change it.
 * @invariant diagnostic-line A diagnostic is printed as `CODE: what (file:line:column)` with its details on indented lines below; no line says what the code means or what to do.
 * @invariant check-limit `check` and `gate` print at most `maxDiagnostics` diagnostics, the ones that matter most, and count the rest by code; `check` counts every diagnostic and `gate` every blocking diagnostic, including in the summary.
 * @invariant review-index `review` without names prints an index: the contracts without a record of their material as it is now, what changed since the recorded review and which invariants that touches; `--all` lists every contract with its status.
 * @invariant review-packet `review <Name…>` carries the lines of the parts that changed since each contract's recorded review and its previous findings, or every file when there is no review to compare with; shared parts appear once with the union of their selected source ranges, and a whole file supersedes its excerpts. Each contract keeps its own fingerprint and findings. `--files all` includes every file whole and `--files none` the references only.
 * @invariant review-touched Where the record cannot tell what a change touches — no part differs by its digest, a previous finding rests on a changed test, an invariant lost its coverage, or anything but a test changed — every invariant is touched.
 * @invariant review-scope-silent The review packet and index never name `REVIEW_SCOPE_LIMIT`; `check` reports it as a fact about the project's setting.
 * @invariant record-refuses `review --record` refuses a verdict for other material, for an unknown contract or invariant, with an invariant left unassessed, or with a finding without a reason or evidence, and then records nothing.
 * @invariant review-stale A change to a contract, the prose of its module, or fingerprinted code, tests, setup or dependencies makes the recorded review outdated, and `check` names the changed parts.
 * @invariant review-code-trivia Under code-v1, ordinary code comments and spacing leave a recorded review current, while syntax, literal contents, annotations and significant directives remain fingerprinted; packets retain the authored source text.
 * @invariant review-fingerprint-legacy Existing unversioned reviews and acceptances retain source-text checking without automatic migration; newly recorded verdicts use the versioned code fingerprint.
 * @invariant review-dependency-relevant Changing a selected imported declaration or a helper it transitively references makes the recorded review outdated.
 * @invariant review-dependency-isolated Changing only an unselected declaration in a dependency that remains eligible for slicing leaves the fingerprint and recorded review current.
 * @invariant review-dependency-fallback When dependency selection or inert module initialization cannot be established under the documented rules, the dependency is fingerprinted whole within the existing traversal bounds, using the record's fingerprint algorithm.
 * @invariant accept `review --accept` records the material of every contract without a fresh record as accepted without a review; `check` asks for no review until it changes and counts acceptances apart from attested ones.
 * @invariant gate `gate` exits 2 on an error and 0 otherwise; missing, outdated or weak reviews block only under `review: "require"`. Its feedback contains only blocking diagnostics, including after three blocks in one session when it lets the agent stop with the report.
 * @invariant locks `lock` records the declarations marked `@final` or `@extendable`; `check` reports a change to a recorded declaration, and `--base` refuses a lock that the base revision has and the lock file no longer does.
 * @invariant codes `codes` prints one line per diagnostic code the harness can emit, with what it means and what to do about it.
 * @invariant init-safe `init` never overwrites a file a person wrote, adds its gate beside other hooks, and passes every path to a hook as data.
 */
export interface Cli {
  (argv: readonly string[], io: CliIo): number;
}

/**
 * @contract
 * @description Loads the project's configuration: the given file, else `.cage/config.json` when it exists, else the defaults.
 * @invariant defaults Without a file the defaults apply; a field left out keeps its default, and `reviewDependencies` is merged field by field.
 * @invariant fields An unknown field, a wrong type or invalid JSON is an `E_CONFIG` for each problem, and the defaults are returned with it.
 */
export interface ConfigLoader {
  (root: string, configPath?: string): LoadedConfig;
}

/**
 * @contract
 * @description The legend of diagnostic codes as text.
 * @invariant legend One line per code the harness can emit, each with what it means and what to do about it; every code the source emits is in it, and nothing else.
 */
export interface Codes {
  (): string;
}
```

## Out of scope

Running tests, judging tests, calling models, reading test runners' reports, Jest, Windows. Selecting individual methods of an implementation or imported class, proving arbitrary JavaScript side effects, and extending dynamic-import tracking are outside the dependency-slicing change. Internal collectors remain implementation details listed in `.cageignore`, not new public contracts.

## Open questions

- A design in a directory with many files is one module: a prose edit in any document outdates every contract's review. Splitting `src/` into directories would narrow that, at the cost of moving files.
- `Cli` carries many more invariants than the `cage-design` skill suggests for one contract, because the command line is the one port of the harness. Splitting it into a contract per command would need the internal report types declared in the design, or methods typed `unknown`; neither checks more than this does.
