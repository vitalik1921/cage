# Пропозиції змін до плану

План: [contract-workflow-mvp.md](contract-workflow-mvp.md). Сам план тут не редагується. Кожен пункт називає правила плану, яких стосується, і має статус:

- **чекає рішення** — код поводиться за планом або тимчасовим рішенням; потрібне рішення власника плану;
- **погоджено** — власник плану прийняв пропозицію; вказано, коли вона реалізується;
- **реалізовано як відхилення** — код уже відрізняється від букви плану; якщо рішення не приймається, треба повернути.

## 1. Чий TypeScript використовує харнес — погоджено 30.09.2026, реалізовано

**Правила:** §2 «Пакет `typescript` із Compiler API; зафіксувати перевірену версію в lockfile» і §7 «Compiler options беруться з цільового проєкту».

**Проблема.** Харнес несе TypeScript 6.0.3. Типові значення опцій залежать від версії компілятора: у TS 6 `strict` типово увімкнений, а `types` типово порожній; у TS 5 навпаки. Тому той самий tsconfig харнес і `tsc` проєкту читають по-різному. `method-os` і `be-linkedbot` працюють на TypeScript 5.x. Для design-фази різниця майже непомітна. На етапі «Зв’язування», коли в Program потраплять реалізації, проєкт на TS 5 без явного `types` отримає хибні помилки про `process`, `Buffer` тощо.

**Рішення.** Брати `typescript` із цільового проєкту (версії 5.x–6.x), а вбудований лишити запасним і для проєктів на TS 7. У звіті `check` видно версію та джерело компілятора. Реалізовано на етапі «Контракти»; перевірено тестом, де той самий дизайн проходить під TS 5.9.3 і не проходить під 6.0.3 через різні типові `types`.

**Уже зроблено окремо (реалізовано як відхилення):** версію зафіксовано на 6.x, бо в TypeScript 7 немає стабільного Compiler API.

## 2. Опції компілятора, які змінює харнес — реалізовано як відхилення

**Правило:** §7 «змінюються лише параметри для `noEmit`».

**Що змінено понад `noEmit`.** `ignoreDeprecations: "6.0"`: без нього tsconfig із `baseUrl` чи `moduleResolution: node10` (звичні для TS 5) дає помилку TS5101 у TS 6. `rootDir` ігнорується: він лише розкладає emit, але відхиляє дизайн поза цим каталогом (TS6059). `noCheck` ігнорується: з ним компілятор не повідомляє помилок типів, і design-фаза проходила б завжди.

**Пропозиція до плану:** «харнес змінює `noEmit`, `rootDir`, `noCheck`, `ignoreDeprecations`; решта опцій — із проєкту». `ignoreDeprecations` задається лише під TypeScript 6: він потрібен, коли вбудований компілятор перевіряє проєкт, написаний під TS 5.

## 3. Коментарі, що вимикають перевірку, у блоках `ts design` — погоджено 30.09.2026, реалізовано

**Правила:** §7 «Compiler diagnostics не приховувати» і §7 «suppression-коментарі … можуть послабити перевірку» (сказано про реалізації).

**Проблема.** `// @ts-nocheck` на початку першого блока вимикав перевірку типів усього дизайну, і design-фаза проходила.

**Реалізовано:** `@ts-nocheck` у блоці — помилка `E_UNSUPPORTED_DECLARATION`.

**Рішення:** `@ts-nocheck`, `@ts-ignore` і `@ts-expect-error` у блоках `ts design` — помилка `E_UNSUPPORTED_DECLARATION`. У реалізаціях і тестах вони лишаються межею гарантії, як у плані.

## 4. Порожній блок `ts design` поруч із непорожнім — реалізовано як відхилення

**Правила:** §4.2 «Кожний знайдений MDX має хоча б один непорожній `ts design` блок» і §11 «`E_DESIGN_BLOCK_EMPTY`: немає непорожнього позначеного source блока».

За буквою плану документ із одним порожнім і одним непорожнім блоком валідний. Харнес повідомляє `E_DESIGN_BLOCK_EMPTY` для кожного порожнього блока: порожній контрактний блок майже напевно помилка автора.

## 5. Поле `version` у конфігурації обов’язкове — реалізовано як відхилення

**Правило:** §4.2 називає помилками unknown fields і неправильні типи, версію, adapter; про відсутню `version` не сказано.

Файл конфігурації без `version` — помилка `E_CONFIG`. Версія потрібна, щоб майбутня зміна формату не читала старі файли мовчки.

## 6. Symlink під час пошуку не обходяться взагалі — реалізовано як відхилення

**Правило:** §4.2 «не обходить symlink поза project root».

Харнес не переходить за жодним symlink, і всередині проєкту теж. Кожен файл знаходиться один раз за власним шляхом, тому окрема дедуплікація канонічних шляхів не потрібна.

## 7. Node.js ≥ 24.11 — уточнення

**Правило:** §2 «Node.js 24 LTS».

`engines` вимагає 24.11: з цієї версії гілка 24 має статус LTS, а `path.matchesGlob` стабільний.

## 8. Де лежать generated-файли і чи комітити їх — варіант B прийнято 30.09.2026; варіант C чекає рішення

**Правила:** §2 «Фіксований output `.design/design.generated.ts` поруч із MDX» і §2 «Для MVP комітити похідні файли; CI перевіряє їхню актуальність. Це обрана конвенція, не вимога MDX».

**Питання власника плану (30.09.2026):** користувачу generated-файли не потрібні; чому б не збирати їх в одній прихованій папці в корені або в `node_modules`?

**Факти.** Самому харнесу файли не потрібні: він перевіряє дизайни з пам’яті. Вони існують для `tsc` і редактора проєкту, щоб реалізації могли написати `import type { Quota } from "./.design/design.generated.ts"`.

**Варіанти.**

| Варіант | Що змінюється | Ціна |
| --- | --- | --- |
| A. Поруч із MDX, у git (зараз) | нічого | кожна зміна контракту двічі в PR |
| B. Поруч із MDX, поза git | `.gitignore` і `design extract` перед `tsc` | після clone типи не працюють до першого `extract` |
| C. Одна прихована папка в корені (`.design/generated/` дзеркалом структури), поза git | те саме, що B, плюс рядок `"rootDirs": [".", ".design/generated"]` у tsconfig проєкту | імпорти в коді й MDX лишаються як у плані (перевірено на TS 6.0.3); контрактні типи можна імпортувати лише через `import type`; інструменти, що не читають `rootDirs`, вважатимуть шлях неіснуючим |
| D. `node_modules/...` | — | менеджери пакетів чистять `node_modules` при встановленні, у Yarn PnP його немає; Prisma відмовилась від такої схеми |

**Рішення.** Прийнято B: у харнесі нічого міняти не треба, це конвенція проєкту; README рекомендує не комітити generated-файли. `extract --check` лишається для проєктів, які їх комітять. Варіант C вирішується після перевірки на реальному модулі. Місце файла задає одна функція, тож перехід пізніше дешевий.

## 9. Уточнення до §6, де план мовчить — реалізовано як відхилення

Рішення, прийняті під час етапу «Контракти». Кожне можна змінити без переробки архітектури.

| Питання | Рішення в коді |
| --- | --- |
| Неекспортована декларація в блоці (§6.1 каже «exported interface/type declarations») | Помилка `E_UNSUPPORTED_DECLARATION`: допоміжний тип теж треба експортувати й позначити `@data` |
| Код для декларації без маркера | `E_UNSUPPORTED_DECLARATION` |
| `@contract Name` або `@data Name` з текстом після тегу | `E_TAG_FORMAT`: ім’я береться з декларації, `@name` відкладено |
| `@description` на полі типу `@data` (§6.2 називає лише contract/data та method) | `E_TAG_LOCATION`; звичайний JSDoc без тегів харнесу на полях дозволений |
| `@invariant` на call signature callable-контракту | Приймається як інваріант контракту загалом (`member: null`) |
| Два інтерфейси з одним ім’ям в одному модулі (TypeScript їх зливає) | Помилка: `E_CONTRACT_DUPLICATE` для двох контрактів, інакше `E_UNSUPPORTED_DECLARATION` |
| JSDoc наприкінці рядка попередньої декларації (§6.3 каже лише «whitespace дозволений») | Не прив’язується до наступної декларації: він стосується попередньої. Тег харнесу в ньому — `E_TAG_LOCATION` |
| Розділовий знак одразу після імені тегу (`@invariant: id …`) | `E_TAG_FORMAT`, а не проза: інакше одруківка мовчки прибирає інваріант |
| Дизайн імпортує власний generated-модуль | `E_DESIGN_IMPORT` |
| `/// <reference path/types/lib>` у блоці | `E_DESIGN_IMPORT`: інакше файли й пакети потрапляють у дизайн в обхід правил імпорту |
| Згадка `@ts-ignore` тощо в коментарі, яку компілятор не розпізнав би | Теж помилка: перевірка навмисно ширша за компілятор |
| `design check` без `--phase` до появи implementation-фази | Помилка аргументів (вихід 2), а не тиха заміна на design-фазу |
| Звіт `check` | Додано `counts.data` і `scope.typescript`, яких немає в прикладі §11 |

## 10. Уточнення до §7 і §8, де план мовчить або суперечить собі — реалізовано як відхилення

Рішення, прийняті під час етапу «Зв’язування».

| Питання | Рішення в коді |
| --- | --- |
| §6.3 «теги не зчитуються з тіла test callback» проти §8 «harness-тег на `t.test` дає помилку» | Зв’язку тег у тілі тесту не створює, але повідомляється як `E_TAG_LOCATION`: інакше автор не дізнається, чому інваріант лишився без тесту |
| Які JSDoc-коментарі звичайних файлів перевіряти (§6.3 «блоки із harness-тегами») | Лише ті, де є тег зв’язування: `@implements`, `@tests`, `@covers` або тег дизайну. `@description` сам по собі — поширений звичайний JSDoc, і він ігнорується |
| `@description` поруч з `@implements` чи `@tests` | Дозволений, значення не має |
| Що рахує `counts.testDeclarations` (§11) | Тестові декларації всередині suite з `@tests`; тести поза контекстом контракту до харнесу не стосуються |
| Тест без `describe` (§8, правило 2: контекст задає suite) | `@covers` дає `E_TEST_CONTEXT`. Файли `node:test` часто пишуть без `describe`; якщо на реальному модулі це заважатиме, варто дозволити `@tests` разом із `@covers` на тесті верхнього рівня |
| Чи повідомляти помилки типів у коді проєкту (§7 «compiler diagnostics не приховувати») | Лише у файлах, де є `@implements`: від їхніх типів залежить висновок харнесу. Решту перевіряє `tsc` проєкту |
| Помилки в дизайні та повна перевірка (§10 «implementation-фаза перевіряє весь scope») | Повна перевірка зупиняється на design-фазі; реалізації й тести позначені у звіті як неперевірені |
| Механізм порівняння (§7, крок 5 дозволяє API або віртуальний файл) | Віртуальний файл із `satisfies`: лише він дає пояснення компілятора, чому реалізація не підходить |
| Exported `let` з `@implements` (§7 каже «exported const») | `E_UNSUPPORTED_DECLARATION` |
| Файли `.mts`, `.cts`, `.tsx`, що збіглися з шаблонами (§2: «`.ts`; без JS/TSX») | Ігноруються: реалізації й тести шукаються лише в `.ts` |

## 11. Адаптер Vitest — погоджено 30.09.2026, реалізовано

**Правило:** §2 «Адаптер декларацій тестів: один, `node:test`; Jest/Vitest — пізніше».

Проєкти власника плану тестуються Vitest, тож без адаптера перевірка на реальному модулі не показала б прив’язки тестів. Додано `"testAdapter": "vitest"`: імпорти з `vitest`, глобальні функції за наявності їхніх типів, модифікатори `.skip` / `.only` / `.todo` / `.concurrent` / `.sequential` / `.fails` / `.shuffle`. Правила `@tests` і `@covers` ті самі.

## 12. Generated-файли необов’язкові — погоджено 30.09.2026, реалізовано

**Правила:** §4.4 і §10: `design check` перевіряє актуальність фізичних outputs; §2: generated TS існує «для TypeScript/IDE».

**Спостереження з реального модуля** ([real-module-trial.md](real-module-trial.md)). У `content-library-api` реалізації не імпортують типи контрактів, а `tsc` проєкту generated-файл не бачить. Файл не має жодного читача, але `design check` без нього падав, і після кожної правки контракту потрібен був `design extract`.

**Рішення власника плану.** Поле конфігурації `generatedFiles`, типово `true` (як у плані). З `false` `check` не вимагає і не читає generated-файли (статус у звіті — `not-required`), а `extract` перевіряє дизайни й нічого не записує. Це доповнює пункт 8: питання, де лежать файли, стосується лише проєктів, де код їх імпортує.

## 13. Типи схеми в дизайні та інфраструктурні параметри — спостереження, чекає рішення

**Правило:** §9 «Імпорти реалізацій, ORM-схем … у design для MVP заборонені. Якщо потрібна зовнішня форма, опиши незалежний DTO на межі».

На реальному модулі це дало дві незручності. Близько третини дизайну — DTO, переписані зі схеми Drizzle та zod. І параметр `db: Database`, який є в кожному методі сервісу, у контракті довелося оголосити як `unknown`: відповідність проходить лише через біваріантність параметрів методів, а контракт про цей параметр нічого не стверджує.

Варіанти на обговорення: дозволити type-only імпорт типів схеми в дизайн (слабшає незалежність контракту від ORM); лишити як є й прийняти дублювання; домовитися про конвенцію для інфраструктурних параметрів. До рішення код не змінюється.

## 14. Один suite — один контракт — спостереження, чекає рішення

**Правило:** §8: `@tests Contract` встановлює контекст suite; `@covers` дозволений лише в цьому контексті.

На реальному коді це двічі вимагало б змінювати тести: файл, де в одному `describe` лежать тести двох функцій (довелося розбити на вкладені `describe`), і файли без `describe` взагалі (у цьому проєкті не трапились, але для `node:test` і Vitest звичні).

**Варіант.** Дозволити `@tests` разом із `@covers` на самому тесті: `/** @tests JoinLines @covers nothing */`. Тоді тест сам називає свій контракт і не потребує окремого suite. До рішення код не змінюється.

## 15. Рівні замка `@final` і `@extendable` — погоджено 30.09.2026, реалізовано

**Правила:** §2 «Lock-рівні `@final`, `@extendable`, `@open`, baseline та API diff — поза MVP»; §6.3 «lock-теги дають `E_UNSUPPORTED_TAG`; не вдавати, що вони enforce-яться».

**Рішення власника плану.** `@final`: інтерфейс ніколи не змінюється. `@extendable`: інтерфейс не можна міняти, але можна розширювати. Без тегу декларація відкрита. Теги мають бути зрозумілі й LLM-агенту.

**Нові коди діагностик** (їх немає в таблиці §11): `E_LOCK_MISSING`, `E_LOCK_VIOLATION`, `W_LOCK_UNRECORDED`, `W_LOCK_OPEN_TYPE`.

**Як реалізовано.** Щоб тег не був лише написом, потрібна точка відліку. Обрано файл `.design/design.lock.json`, який пише команда `design lock` і читає `design check`. Уже записане `design lock` не змінює; замок знімається лише ручною правкою файла. Теги дозволені на контрактах і типах даних. `@open` лишається непідтриманим: відкритість — це відсутність тегу.

**Уточнення власника плану, 30.09.2026.**

- Замок контракту охоплює й інваріанти. `@final`: жодного не можна змінити, додати чи прибрати. `@extendable`: наявні не змінюються, нові додавати можна.
- Якщо замкнена декларація використовує контракт чи тип даних без замка, харнес попереджає (`W_LOCK_OPEN_TYPE`). Автоматично замок на такі типи не поширюється: рівень для кожного обирає автор.
- Файл-замок можна обійти, видаливши запис. Тому `design check` отримає порівняння з гілкою Git: усе, що замкнено там, має лишитися замкненим і незмінним.

## 16. Покриття дизайном і `.design/ignore` — погоджено 30.09.2026, реалізовано

**Правило:** плану такого правила немає; §4.1 визначає лише, що файл належить найближчому модулю-предку.

**Рішення власника плану.** Харнес попереджає про інтерфейси модуля, не покриті дизайном. Модуль має список ігнорування для файлів і папок: для LLM він означає «для цього дизайн генерувати не треба», для харнесу — «не попереджати».

**Новий код діагностики** (його немає в таблиці §11): `W_NOT_DESIGNED`.

**Як реалізовано.** «Інтерфейсом» вважається exported `class`, `function` або `const` у модулі з дизайном, тобто те, на чому може стояти `@implements`. Без тегу — попередження `W_NOT_DESIGNED`. Список — файл `.design/ignore` у модулі, формат як у `.gitignore`.

**Питання, що лишились.**

- TS-типи в коді (`interface`, `type`) не перевіряються: у плані немає тегу, який пов’язує тип у коді з `@data` у дизайні.
- Код поза модулями з дизайном не дає попереджень. Чи попереджати про каталоги, де дизайну немає взагалі?
- Ігнорування працює для файлів і папок. Окрему декларацію у файлі проігнорувати не можна.
